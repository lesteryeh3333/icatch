SDK RELEASE PROCESS — 內部說明

為什麼我們必須改變 SDK Release 流程

BSP 11.5.1 / DMP-415 事件回顧，以及新流程解決了什麼問題

背景補充・個人觀察

舊流程為何需要 Beta 版本

以下是個人推測，非已與 DMP 明確確認過的結論，僅作為理解舊流程動機的參考。

在原本 6 週的流程裡，「先出一版 Beta 給 DMP、再等 DMP 回饋」是整個時程的核心節點。這個安排背後，DMP 真正想要的其實是能跟 iCatch 同步驗證，而不是被動等 iCatch 這邊先測完、有問題才發現，導致 release 時程被拖延。

往深一層想，這個訴求追根究柢，很可能反映的是 DMP 對 iCatch 內部測試細節掌握度的不信任——不確定 iCatch 到底測了什麼、測得夠不夠深，所以需要盡早拿到 Beta 版本自己驗證，用自己的驗證結果來確認風險，而不是單純信任 iCatch 這邊回報「測過了、沒問題」。這正是新流程要處理的核心問題之一：不是加快交付 Beta 的速度，而是讓 DMP 在 Beta 釋出前，就能看到 iCatch 已經用同等標準先驗證過。

釐清主因與次因

測不到，不是因為測項不夠多

測項數量從來不是問題所在，問題出在測的東西從一開始就不是客戶在用的東西。

確實發生過：時程壓力 → 測試項目被壓縮（BSP 11.5.1 真實情況）
→
但這只是助長因素，不是根本原因

問題出在測項的設計邏輯、測試資源配置、與測試時機安排這三個系統性層面，不是靠增加測項數量就能補上的缺口。

根因分析

三個結構性缺口

缺口 1

Customer Scenario Gap

iCatch 內部 QA 測項的設計邏輯以自身功能驗證角度出發，未對齊 DMP 實際操作情境；非測項數量不足，而是測項未涵蓋真實使用場景，增加測項數量無法補上這個缺口。

缺口 2

Reproduction Gap

可調度樣本僅 1 台 SOM board，測試機器數量不足限制了並行驗證與交叉比對的能量，需增加測試機器以提高重現率。

缺口 3

流程時序錯亂

Full Test 要到正式 release 前才真正跑完，Beta 釋出當下其實並未完成全部測試，等於客戶比 iCatch 更早做深度驗證。

具體板子需求：現況 1 台 → 需求 3 台（＋2 台）

  • 1 台：QA 手動執行 DMP 測項驗證（W3 起優先驗證用）
  • 2 台：長時間可靠度測試持續運行，支援並行驗證與交叉比對（排除單板硬體個體差異造成的機率性問題）

此為 SOM board（與客戶同款 Sensor），非 EVB；EVB 可作為常規/非 Sensor 相關驗證之補充樣本，但無法取代 SOM board 於 DMP 測項驗證上的角色。

缺口 1 詳解

DMP 測項與 iCatch 測項的差異

總結兩點

  • 問題不是 iCatch 完全沒測，而是 iCatch 現有測項庫裡，v4l2loopback、CPU Clock 調整、GPIO 實際驅動輸出、ADC/PWM 這幾塊完全沒有對應項目，是真正意義上的「沒測到 DMP 會測的東西」；A3000 NPU 與 Stereo Vision（Depth Engine）則屬於 DMP 產品線專屬硬體模組，iCatch 其他平台未必配備，沒測不是通用能力被漏掉，而是本來就屬於 DMP 專屬側的驗證範圍（其中 SV 根頁面索引雖列有「SV 自動化測試」規劃，但未建成分頁、無附件、無判定機制，屬於規劃了卻沒落實的執行落差）
  • DMP 的測項範圍比想像中廣，不是只測 codec/CV 這種核心功能，還系統化涵蓋了板級周邊：GPIO 實際驅動輸出、SPI/RTC/periinfo 列舉、CPU Clock 調整（含暫存器真值驗證與 deadman watchdog）、ADC/PWM。這些在 iCatch 內部測項庫裡，目前只在 01-system 分頁有零星文字步驟提及（如 reset/watchdog），沒有 DMP 這種嚴謹的自動化判定機制

彈性機制

7 週標準 ＋ 條件式 +1 週

7 週是標準週期，非死板天數。當特定條件觸發時，系統性多留一週，而非每次都預先犧牲這一週，也不是臨時硬趕。

觸發判斷點（對應既有 Gate 檢查時間）

  • W5 週三（Beta Gate）：若 W3-W4 驗證後仍有 Critical（會當機）問題未解決、或 root cause 仍未定位清楚，於此時點評估是否需延後 Beta。這是 Beta 前的最後防線，逾此時點才發現的問題已無足夠緩衝，必須在此前決斷
  • W6 週四（Release Gate）：客戶於 W6 整合測試期間，可能於任一天回報問題（含新增測項發現者），不限於週初；若問題複雜、於週四評估無法在週五前收斂，不代表立即觸發 +1 週——仍有機會於 W7 一~二 Retest 期間收斂；僅在確認 W7 仍無法收斂時，才正式觸發 +1 週

安全閥：+1 週用完仍未解決時，不得再自動延長

7 週 → 8 週是機制內建、可預期的一次性延長。若第 8 週結束問題仍未收斂（例如 root cause 持續難以定位），不得再依同一套機制自動延到第 9 週，必須跳出來走正式 Risk Acceptance 決策，二擇一：

  • 正式決定再延：需簽核、留下正式紀錄，不能默默拖延
  • 帶已知風險 Release：明確記錄哪些問題尚未解決、風險評估與緩解措施，經簽核後才可放行

核心原則：不能像 11.5.1 為了 release 時間到了就默默地把測項減少。

Beta 釋出後，客戶自行新增測項的處理

DMP 可能在 W6 整合期間，自行新增原先未涵蓋的測項並測出問題。判斷標準與既有規則一致，唯一閘門是「是否為 Critical」：

  • 發現 Critical（會當機）問題：不論是否為原先承諾涵蓋的測項，一律納入 W6 末的問題收斂判斷，可能觸發 +1 週彈性
  • 非 Critical：記錄後排入 W7 一~二的下一版新測項窗口，不影響本次 W7 時程

核心原則：只有 Critical 能觸發延遲，不能讓「客戶持續新增測項」本身變成無限期拖延 release 的理由，否則 Gate 機制形同虛設。

新測項如何併入下一版 DMP 測項清單

無論是 W6 客戶自行新增、或 W7 一二正式提交的下一版新測項，都須正式併入 DMP 測項清單，而非直接排入開發規劃。併入方式比照 Multi-product Coupling 章節所定義的評估機制：先判斷與 iCatch 現有測項是否重複（找交集）、記錄執行工時（更新測項工時對照表），再依數量與複雜度決定是否需要觸發完整評估空窗期，或可直接排入 N+1 的 W1 消化——不是每次新增測項都重新從零評估。

尚未解決的缺口

Multi-product Coupling — 多產品共用同一 BSP Release Train

目前整套流程只解決了 DMP 這一條產品線；BSP release train 上還有其他產品線共用同一份 code base 與同一個 release 日期，這件事目前尚未有具體解法。

現況

其他產品線目前仍停留在功能測試 + 個別壓力測試

DMP 因這次事件已被迫拉高到含長時間可靠度測試與 Customer Scenario 的驗證水準；其他產品線尚未導入。若不釐清邊界，可能出現兩種風險：DMP 的高規格被迫套用到其他產品線（QA 資源直接不堪負荷），或其他產品線的 change 影響到共用底層（如 Encoder），卻只有 DMP 在做長時間驗證，問題持續被漏掉。

解法方向：BSP Core + Product Profile

BSP Core（全產品共同）

共用底層，強制執行

Kernel / ISP driver / Memory / IPC，以及 Encoder（H264/H265/MJPG）與長時間可靠度測試 — 已確認 Encoder 為所有產品共用模組，長時間可靠度風險不是 DMP 專屬，應拉進 Core，全產品受益、不需各自重跑。

Product Profile（各產品專屬）

在 Core 之上疊加

DMP Profile：Face AE、Customer Scenario 等 DMP 專屬測項。其他產品線維持現有功能測試 + 壓力測試，不強制比照 DMP 拉高規格，除非該產品線自己也發生類似事件。

執行前置：一次性 2 週整合評估空窗期

Step 1：盤點 DMP 完整測項 ∩ iCatch 現有測項
找出重複項（合併）、DMP 獨有項、iCatch 原有項；已完成初版比對，見 dmp-icatch-comparison.html
→
Step 2：完整跑一輪，記錄每項工時
建立「測項工時對照表」，作為未來時程評估依據
  • 此 2 週為第一次系統化分析客戶完整測試腳本所需的一次性投入，非每輪 release 固定週期
  • 正式排定 2 週長度前，須先看過雙方 script 內容，確認測項規模後再校準此數字
  • 之後客戶提交的新增測項（W7 一~二窗口），若能對應到既有工時對照表的類型，直接排入下一輪 W1 消化，不需再走完整 2 週；僅在測項數量多或全新場景時，才視情況觸發較短的評估期

自動化測試：列為第二階段

測項集合尚未穩定前投入自動化，容易發生腳本做到一半、測項又調整的白工。順序應為：先人工跑穩、測項與工時定案 → 再投入自動化，並依工時對照表排定自動化優先順序。

產出物：iCatch 標準測項文件

正式文件化 BSP Core + 各 Product Profile 測項清單，並標註每項來源（iCatch 原有／DMP 提供／兩者合併）。每次 release 可附上「本次驗證涵蓋範圍」，作為對客戶主動告知涵蓋範圍時的具體依據，而非空泛承諾。

被漏掉的省思

iCatch 測試深度，目前沒有客觀標準

「客戶發現的問題會被納入測項」只證明 iCatch 有在學習，不能證明現在的測試「已經夠細」——這兩件事邏輯上是分開的，不能互相替代。

會被直接挑戰的問題

「你們有把客戶發現的問題補回測項，那下一個還沒被客戶發現的問題呢？你們怎麼知道測項『現在』夠細，而不是又要等客戶測出來才知道？」— 目前的 regression 機制是被動補強（不重演已發生的問題），不是主動的測試深度管理，沒有回答「多細才算細」這個問題。

→
Phase 2：訂定 iCatch 測試深度分級標準

  • Phase 1 不是新增工作：與 Multi-product 章節「盤點 DMP 測項 ∩ iCatch 現有測項」是同一件事，用 DMP 標準當作檢視基準，找出 iCatch 現有測項在深度上（非只有覆蓋範圍）的落差
  • Phase 2 屬於下一階段討論，此時尚未展開，需先有 Phase 1 的具體掃描結果（哪些項目深度不足、不足在哪）才有依據訂標準，避免憑空定規則
  • 可能的分級方向（待 Phase 1 結果確認後細化）：依 Risk Level（Critical / High / Medium / Low）決定對應之驗證深度，與 Change Impact Matrix 邏輯一致
